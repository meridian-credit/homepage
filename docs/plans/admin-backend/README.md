# 관리자 페이지와 백엔드 계획: 통합안

2026-09-30. 같은 brief(`brief.md`)로 두 모델이 서로의 답을 보지 않고 따로 계획을 세웠고, 여기서 합쳤다.
- Claude Opus 5.5, xhigh: 원문 `reviews/claude.md`
- gpt-6-astra, medium: 원문 `reviews/astra.md`

두 안이 갈린 곳은 평균 내지 않았다. 한쪽을 골랐고, 판단을 가르는 사실은 직접 확인했다(§1 끝의 표).

## 한 줄 결론

운영을 Vercel 에서 자체 서버로 먼저 옮긴다. 그 서버의 **SQLite 파일 하나 + Drizzle** 로 콘텐츠를 옮기고, 이 저장소 안에 한국어 관리자를 만든다.
- 관리자는 **별도 호스트**(`admin.meridianco.kr`)로 연다.
- 공개 페이지는 지금처럼 빌드 때 정적으로 만든다. 게시하면 사이트 전체를 한 번 갱신한다.
- 문의는 계속 저장하지 않는다.
- 첫 단계에 하루짜리 검증을 둔다. **Payload 를 쓸지 직접 만들지**, 표가 많은 글을 **위지윅 편집기로 편집할지**를 여기서 정한다.

### DB 와 순서를 이렇게 정한 까닭

두 안의 차이는 결국 **운영이 Vercel 에 남느냐** 하나다.
- Astra 도 "자체 서버 이전이 먼저 끝나고 영속 볼륨과 복구 담당자가 확정되면 SQLite 가 경쟁력이 있다"고 적었다.
- 그 전제는 이미 서 있다. 주인은 2026-09-28 에 "Vercel 은 안 쓸거고"라고 했다. dev 는 이미 자체 서버에서 돈다.
- Vercel 의 Git 연동은 저장소 이전 뒤 끊겨 있다(2026-09-30 기준 미해결). 지금 운영으로 가는 길 자체가 이전을 거쳐야 한다.

그러면 한 서버, 한 프로세스, 글 60편 규모에서 SQLite 가 더하는 운영 부담이 가장 적다.
- DB 서버도 포트도 업그레이드도 없다. 백업은 파일 하나다.
- 읽기가 동기라 `getAllPosts()` 같은 함수 모양이 그대로다(`src/lib/posts.ts`).

Vercel 을 떠나지 못하게 되면 Astra 안(Neon + 객체 저장소)이 대안이다. 두 안 다 Drizzle 이라 방언을 바꾸는 값이 초기에는 작다.

**직접 확인한 사실**

| 사실 | 확인 방법 |
|---|---|
| Payload 3.90.2 가 Next 16.3.4 를 지원한다 | `npm view @payloadcms/next peerDependencies` |
| `@tiptap/markdown` 3.31.3 이 있다 | `npm view` |
| 글 53편 중 49편에 표가 있고, JSX·중괄호·HTML 은 0편이다 | `content/posts` 를 셈 |
| `/contract` 가 같은 origin 으로 넘겨진다 | `next.config.ts:75` |
| 검색·llms 응답이 `max-age=3600` 이다 | `src/app/api/search/route.ts:69`, `src/app/llms.txt/route.ts:56` |
| 자체 서버의 `infra-postgres` 는 다른 프로젝트 스택의 것이다. 함께 쓸 DB 가 아니다 | `/opt/stacks/infra` |

## 2. 두 안이 따로 같은 데 닿은 것 (AGREED)

- **DB 로 가는 이유가 생겼다.** 예전 "하지 않기로 한 것"의 DB 기각은 편집 수요가 없을 때의 판단이었다. 비개발자 편집 요구가 생겼으니 콘텐츠 DB 는 된다.
- **여전히 만들지 않는 것:** 문의 저장, CRM, 메일 큐. 이유도 그대로다(`docs/plans/ui-ux-remediation/backend-backlog.md`).
- **문의:** 저장하지 않는다. 대신 BE-01(발송 실패를 성공으로 답함)을 먼저 고친다.
- **Git 기반 CMS(Keystatic 등)는 기각.** 공개 저장소라 초안이 공개되고, 게시마다 빌드·배포를 거친다.
- **구조:** 별도 API 서버 없이 이 Next 앱 하나로 간다.
  - Drizzle 로 마이그레이션한다(SQL 을 검토한 뒤 명시적으로 실행).
  - Zod 스키마 하나를 관리자·서버 액션·공개 읽기·이전 스크립트가 같이 쓴다.
  - 쓰기는 Server Actions 로 하고, 모든 액션에서 세션과 권한을 다시 확인한다.
- **공개 페이지:** 정적 prerender 를 유지한다. 공개 페이지에서 `cookies()` 나 `draftMode()` 를 쓰지 않는다. Cache Components 전환은 이 일과 묶지 않는다.
- **미리보기:** 로그인한 관리자 경로에서 실제 렌더러로 그린다. 새 탭으로 연다(`frame-ancestors 'none'` 때문에 iframe 불가).
- **주소:** slug 는 처음 게시한 뒤 잠근다. 기존 URL 은 그대로라 redirect 가 필요 없다.
- **`content-audit.mjs` 규칙은 게시 검증으로 옮긴다.** 세율·기한·기준금액·법 개정을 다루는 글은 출처와 검토일이 **필수**다(지금은 경고). 과거 글을 검토일 일괄 갱신으로 통과시키지 않는다.
- **이전:** 한 방향 import 를 하고, 전후 HTML 을 비교하는 관문을 둔다. 같은 종류를 코드와 DB 양쪽에서 동시에 편집하지 않는다. 비공개 글 3편은 이미 git 이력에 공개돼 있다는 점을 적어 둔다.
- **검색:** 모듈 전역 캐시를 없앤다(게시 뒤에도 옛 색인이 남는다). 검색 서버는 따로 두지 않는다.
- **백업:** 매일 외부로 내보내고, 분기마다 복원 연습을 한다. 마이그레이션은 더하기만 하고(expand), 지우기·이름 바꾸기는 다음 배포로 미룬다(contract).
- **route group 분리:** 공개 사이트와 관리자를 나눈다. catch-all 라우트는 `/contract` rewrite 를 가리므로 만들지 않는다.

### 1단계: 검증 관문 (1–2일)

결과는 `docs/plans/admin-backend/spike.md` 에 적는다.

1. **Payload 대 직접 제작.** FAQ 와 표가 가장 많은 글 한 편으로 잰다. **전부 통과하면 Payload 를 쓴다.**
   - Next 16.3.4 에서 빌드된다.
   - 관리자 화면이 `eval` 없이 CSP 안에서 돈다(관리자 호스트에 따로 정책을 둬도 된다).
   - 한국어 화면이 된다.
   - 표 글이 왕복 뒤 같은 HTML 로 나온다.
   - 공개 페이지 prerender 가 그대로다.
   - `npm audit` 가 새로 막히지 않는다.
2. **위지윅.** `@tiptap/markdown` 으로 표 49편을 불러왔다가 다시 저장해, 공개 HTML 이 같은지 본다. 한 편이라도 다르면 Markdown 입력칸 + 도구줄 + 표 붙여넣기로 간다.
3. **dev 에서 실제로 확인할 것.**
   - Better Auth 가 Next 16.3.4 에서 돈다.
   - Caddy → NPM 두 겹 뒤에서 Server Actions 의 Origin/Host 검사가 통과한다.
   - `proxy.ts` 로 `admin.` 호스트를 나눈다.
   - `revalidatePath('/', 'layout')` 가 route group 페이지와 route handler 까지 닿는다.
   - 게시 직후 첫 방문자가 옛 페이지를 한 번 보는지 잰다.

>   - 공개 layout 을 옮기지 않아도 되고, `main` 에는 관리자 화면이 실리지 않는다.
>   - 그래서 `proxy.ts` 로 호스트를 나누지 않는다.
> - **역할이 없다.** 허용 목록(`ADMIN_EMAILS`)에 있으면 저장하고 바로 반영한다. 「편집자는 게시하지 못한다」는 역할을
>   들일 때 다시 본다.
> - **`faq.ts`·`schedule.ts` 의 배열을 남겼다.** 운영(Vercel)이 아직 DB 없이 이 배열을 읽는다. 운영을 옮길 때 지운다.
> - **`NEXT_SERVER_ACTIONS_ENCRYPTION_KEY` 를 고정하지 않았다.**
>   - 관리자 액션은 클로저를 쓰지 않는다.
>   - 배포 전에 연 화면도 코드가 같으면 그대로 저장된다(재빌드로 확인).
>   - 요청이 실패하면 「새로고침해 주세요」가 나오고, 적던 내용은 화면에 남는다.
> - **백업은 서버 안 매일 사본(30일)만 있다.** S3 반출과 복원 연습은 운영을 옮길 때 한다.
>
> 계획대로 한 것:
> - 저장 순서는 「권한 → 검증 → 트랜잭션(판 번호 확인 · 감사 기록) → 전체 갱신」이다.
> - 빌드는 DB 사본을 읽는다. 사본은 이미지 층에 남지 않고, 사본이 없으면 빌드가 실패한다.
> - noindex, no-store.
> - 공개 서버는 뜰 때마다 스스로 모든 쪽을 다시 그리게 한다(`src/instrumentation.ts`).
>   - 「다시 그리기」 표시는 메모리에만 있고, 되돌린 이미지는 빌드 때 사본에서 시작한다.
>   - 그래서 저장 뒤의 재시작·되돌리기에도 DB 의 지금 내용이 나온다.
> - CI 에서 better-sqlite3 를 rebuild 하고 관리자 e2e 를 돌린다.
>
> 수용 기준 확인(`admin/tests/admin.spec.ts`, 10건):
> - 세션이 없거나 허용 목록 밖이면 화면과 액션이 거절된다. 액션은 화면을 거치지 않은 요청으로도 확인했다.
> - FAQ 를 고치면 `/faq` · `/contact` 에 반영된다.
> - 사본 DB 로 빌드해도 `/contact` 는 prerender 그대로다.

이 단계만으로도 가치가 선다. 대표가 개발자 없이 세무 일정을 채우고 FAQ 를 고친다.
- **기반:** SQLite(WAL)와 Drizzle 스키마·마이그레이션, 공용 Zod 스키마.
  - `src/server/db`, `src/server/content/{read,write}`.
  - 쓰기는 늘 "권한 → 검증 → 트랜잭션 → 감사 기록 → 전체 갱신" 순서다.
- **라우팅:** 공개 페이지를 `(site)` route group 으로 옮기고, 관리자는 `admin.` 호스트로 둔다. `noindex`, `private, no-store`, robots·sitemap·검색에서 제외.
- **Better Auth:** 가입 막음, 서버 CLI 로 계정 생성, 역할 둘, 민감한 작업은 다시 로그인.
- **일정·FAQ 를 DB 로 옮긴다.**
  - 헤더의 일정 큐브는 layout 이 prop 으로 받는다(`schedule-cube.tsx` 가 직접 import 하던 것을 바꾼다).
  - `faq.ts` 와 `schedule.ts` 의 배열을 지운다.
- **배포:**
  - 빌드는 DB 스냅샷(online `.backup`)을 읽는다. 스냅샷은 이미지 층에 남기지 않는다.
  - DB 가 없으면 빌드가 **실패**한다. 빈 사이트를 prerender 하지 않는다.
  - `NEXT_SERVER_ACTIONS_ENCRYPTION_KEY` 는 배포 사이에 고정한다.
- **백업:** 매일 DB 와 업로드를 S3 서울(ap-northeast-2)로 보낸다. put 전용 IAM, 90일. 대시보드에 마지막 백업 시각을 보인다. 복원 연습을 1회 한다.
- **CI:** 시드 DB 와 테스트 관리자, `better-sqlite3` rebuild. `schedule-check.yml` 은 대시보드 경고로 바꾼다.
- **수용 기준**
  - `/contact` · `/blog` prerender 검사가 그대로 통과한다.
  - 세션이 없으면 관리자와 액션이 거절된다.
  - FAQ 를 고치면 `/faq` · `/contact` 와 JSON-LD 에 반영된다.
  - 편집자는 게시하지 못한다.
  - `measure.mjs` 가 예산 안이다.
  - dev 에서 복원 연습이 성공한다.
- **되돌리기:** PR 을 되돌리고, DB 에서 내보낸 JSON 을 TS 배열로 되돌린다.

## 6. 문의 메일 경로

메일은 우리 AWS 계정의 Amazon SES(서울, ap-northeast-2)로 보낸다. `@aws-sdk/client-sesv2` 로 SES 의 HTTPS API 를
부른다(`src/app/api/contact/route.ts`). SMTP 서버는 두지 않는다. 2026-10-01 에 Resend 에서 옮겼다(주인 결정).

| 항목 | 지금 값 |
|---|---|
| 보내는 주소 | `CONTACT_FROM_EMAIL` = `no-reply@meridianco.kr`, 필수. 없으면 500 으로 답하고 보내지 않는다 |
| 보내는 도메인 | `meridianco.kr`. SES 에 등록했고, DNS 는 2026-10-01 에 우리 Cloudflare 로 옮겼다. DKIM CNAME 3개, MAIL FROM `e.meridianco.kr`(MX·SPF), DMARC `p=none` |
| 받는 주소 | `CONTACT_TO_EMAIL`, 없으면 `siteConfig.email` = `mscpa@dscpa.co.kr`. 받는 쪽 메일 서버는 `spam.g2w.kr`(스팸 필터) |
| 회신 | Reply-To = 문의자 이메일. 받은 메일에서 [답장] 하면 문의자에게 간다 |
| 키 | `AWS_ACCESS_KEY_ID`·`AWS_SECRET_ACCESS_KEY`. `no-reply@meridianco.kr` 로만 보낼 수 있는 키를 서버 `.env` 에 둔다 |

**서버를 옮기면서 할 일**
- ~~BE-01, BE-02~~ 2026-10-01 코드 완료. 남은 것은 SES 도메인 인증이 끝난 뒤 dev 에서 시험 수신함으로 한 번 보내 보는 것이다.
- **Resend 정리:** 지금 운영 중인 빌드는 아직 Resend 로 보낸다. 새 코드가 운영에 올라간 뒤 DNS 의 `resend._domainkey`·`send.` 레코드를 지운다.
- **속도 제한:** 서버가 한 대라 메모리 속도 제한으로 충분하다. Upstash 를 빼면 `CONTACT_RATE_LIMIT_REQUIRE_SHARED` 는 켜지 않는다. 켜면 문의가 전부 503 이 된다.
- **처리방침(BE-07):** 문의 내용은 우리 AWS 계정의 SES 서울 리전을 거친다. 수탁사로 AWS 를 적는다. 국외 이전 항목은 법무가 판단한다.

## 7. 주인이 정할 것 (기본값은 굵게)

**정해진 것 (2026-09-30, 주인 확인)**
- DB 는 **SQLite**.
- 운영은 Vercel 을 떠나 우리 서버로 옮긴다. `~/.ssh/config` 의 서버 중 하나를 쓴다.
  - 권하는 자리: proxmox-w 에 전용 VM 을 새로 만든다. 여유 32코어 · 메모리 95GB.
  - 접속 경로는 지금 dev 와 같다: `proxy-seoul-01`(Caddy) → tailnet → 새 VM.
  - hometax-w 에는 두지 않는다. 고객 홈택스 자료를 모으는 VM 이라, 인터넷에 열린 사이트와 관리자 로그인이
    한 기계에 서면 사이트 쪽 사고가 고객 세무 자료로 번진다.
- 이 결정으로 Neon 대안은 닫는다.
- **문의는 메일로만 받는다.** DB 에 넣지 않는다. 관리자에 문의함도 두지 않는다.

**남은 것**

1. 새 VM 의 이름과 크기: **2–4 vCPU · 4–8GB · 40GB, proxmox-w**.
2. 로그인 수단: 사무소가 Google 계정(2단계 인증)을 쓰는가? **쓰면 Google 로그인**, 아니면 비밀번호 + TOTP.
3. 편집자도 게시할 수 있는가: **아니오**(세무 글은 대표 회계사를 거친다).
4. 관리자 주소: **`admin.meridianco.kr`**. Gabia DNS 에 레코드 하나가 든다.
5. Payload 대 직접 제작: **1단계 검증 결과로 정한다**.
6. 글 편집 화면: **위지윅(Markdown 저장)**. 표 왕복 검증을 통과했을 때만.
7. 4단계(서비스·고객유형·사무소 정보)를 할지: **한다**.
9. 백업: **매일 S3 서울 · 90일 · 분기별 복원 연습**.
10. 화면에 쓰지 않는 `seriesLabel` / `seriesNumber`(3편): **뺀다**.

인증 방식, 이전 시점과 방식, 운영 호스트는 이 문서가 권하는 것일 뿐이고 승인을 대신하지 않는다.
