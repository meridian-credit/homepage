## 현재 구조와 결론

- **데이터베이스는 필요 없다.**
  - 서비스·구성원·일정·블로그는 모두 코드와 MDX 파일이다.
  - 문의는 저장하지 않고 메일로만 보낸다. 받은편지함이 곧 저장소다.
- **서버 기능은 세 가지다.** `POST /api/contact`(우리 AWS 의 SES 로 메일 발송), `GET /api/search`, `llms.txt`.
  - Upstash Redis 는 선택 사항이고, 도배 방지 카운터로만 쓴다.
- **고객 포털과 계약은 별도 앱이다.**
  - 고객 포털: `siteConfig.clientPortalUrl` = `hometax-dashboard.vercel.app`.
  - 계약: `/contract` 가 taxchat 으로 rewrite 된다.
  - 두 앱의 백엔드는 이 저장소에서 판단할 수 없다.
- **운영 중인 `main` 도 문의 API 코드가 같다.** BE-01·BE-02 는 2026-10-01 에 `dev` 에서 고쳤고, `main` 에 합치기 전까지
  운영에는 결함이 남아 있다.

## 항목

### BE-01 — 발송 실패를 성공으로 답한다 (P0, 2026-10-01 완료)

> **고친 것:**
> - 발송을 Resend 에서 우리 AWS 계정의 SES(서울)로 옮겼다(2026-10-01, 주인 결정). 보내는 주소는 `no-reply@meridianco.kr`.
> - SES SDK 는 거절·권한 오류·연결 실패 때 예외를 던진다. 라우트는 그때와 `MessageId` 가 없을 때 502 와 함께
>   「잠시 후 다시 시도하거나 대표 메일로 직접 보내 달라」고 답한다. 로그에는 오류 이름·상태만 남는다.
> - 보내는 주소(`CONTACT_FROM_EMAIL`)가 비면 보내지 않고 500 이다. 시험용 주소로 떨어지는 길은 없다.
> - 검사: `tests/e2e/contact-route.spec.ts`. 예외를 삼키고 성공으로 답하게 바꿔 돌리면 두 테스트가 200 을 받아 실패한다(확인함).
>
> 아래는 고치기 전 기록이다.

- **코드:** `src/app/api/contact/route.ts:476` 이 `await resend.emails.send(...)` 의 결과를 버리고, `:512` 에서 무조건 `{ success: true }` 를 돌려준다.
  - Resend SDK 6.x 는 실패해도 예외를 던지지 않는다. `{ data: null, error }` 를 돌려주므로 `:516` 의 `catch` 까지 가지 않는다.
- **증상:** 키 폐기, 도메인 인증 해제, 한도 초과 때 방문자는 "접수되었습니다"를 보지만 메일은 오지 않는다.
- **같은 경로의 실패:** `:456` 은 `RESEND_FROM_EMAIL` 이 비어 있으면 Resend 테스트 주소 `onboarding@resend.dev` 로 넘어간다.
  - 이 주소는 계정 주인에게만 보낼 수 있어서, 결과는 같은 조용한 실패다.
- **할 일:**
  - `error` 가 있거나 `data?.id` 가 없으면 502/500 으로 답하고, 오류 이름만 로그에 남긴다(본문·주소는 남기지 않는다).
  - 발신 주소가 비어 있으면 fallback 하지 않고, 키가 없을 때처럼 설정 오류로 답한다.
- **검사:** SDK 가 `{ data: null, error }` 를 돌려줄 때 200 이 아닌지 확인한다. 방법은 BE-02 의 실제 발송 테스트에 적었다.

### BE-02 — 문의 경로 보완 (P1, 2026-10-01 완료. 카운터 키 해시는 BE-07 과 같이)

> **고친 것:**
> - 시계: 폼이 `performance.now()` 로 잰 `elapsedMs` 를 보내고, 서버는 범위만 본다. 배포 순간에 열려 있던 옛 폼은
>   `startedAt` 을 보내므로 「새로고침」 안내를 한 번 받는다. 배포를 되돌릴 때도 새 폼 → 옛 서버로 같은 일이 한 번 생긴다.
> - 받는 주소: `CONTACT_TO_EMAIL`, 없으면 `siteConfig.email`.
> - 실제 라우트 테스트: `contact-route.spec.ts` 가 따로 띄운 `next start` 를 가짜 SES(`AWS_ENDPOINT_URL_SESV2`)에 물려
>   성공·SES 거절·연결 실패·너무 빠른 제출을 확인한다. 진짜 키가 있는 서버에는 보내지 않는다.
> - Upstash `reason: "timeout"` 은 Upstash 오류와 같이 다룬다. `REQUIRE_SHARED` 면 503, 아니면 메모리 카운터.
> - 안 쓰는 다섯 필드와 `src/lib/contact-options.ts` 를 지웠다. 메일 제목은 `[홈페이지 문의] 이름` 이다.
> - **남은 것:**
>   - 실제 사이트를 돌리는 서버에 이 코드를 올리기 전에, 그 서버에 `CONTACT_FROM_EMAIL` 과 SES 발송 키가 있는지
>     확인한다. 없으면 모든 문의가 500 또는 502 가 된다.
>   - meridianco.kr 네임서버가 Cloudflare 로 넘어가 SES 도메인 인증이 끝나면, dev 에서 시험 수신함으로 실제로 한 번
>     보내 보기. dev 에는 키보다 `CONTACT_TO_EMAIL` 을 먼저 넣는다.
>   - 카운터 키 해시(BE-07).
>
> 아래는 고치기 전 기록이다.

- **기기 시계 차이.** `contact-form.tsx:35` 는 시작 시각을 브라우저 시계로 찍는다. `route.ts:420–437` 은 경과 시간을 서버의 `Date.now()` 로 잰다.
  - 예: 시계가 5분 빠른 PC 에서 2분 동안 쓰면 경과 시간이 음수라 계속 400 이 나고, 새로고침해도 풀리지 않는다.
  - 고칠 방향: 경과 시간을 클라이언트에서 재서 보낸다. 서버는 범위만 확인한다.
- **받는 주소가 코드에 고정돼 있다.** `route.ts:478` 이 `to: [siteConfig.email]` 이다.
  - dev 에 Resend 키를 넣는 순간 테스트 문의가 실제 고객 창구로 간다.
  - `CONTACT_TO_EMAIL` 환경 변수를 두고, 없으면 `siteConfig.email` 로 보낸다. **dev 에 키를 넣기 전에 필수다.**
- **실제 API 를 부르는 테스트가 없다.** 문의 e2e 는 전부 `page.route` 로 응답을 가짜로 채운다. BE-01 이 지금까지 안 잡힌 이유다.
  - Resend SDK 는 `RESEND_BASE_URL` 을 읽는다. 테스트 서버를 가짜 Resend 로 향하게 한다.
  - 그 상태로 성공, `{ error }`, 연결 실패 세 경우를 실제 라우트로 확인한다.
  - 실제 발송 검증은 승인된 테스트 수신함(`CONTACT_TO_EMAIL`)으로만 한다. 운영 `/api/contact` 에는 보내지 않는다.
- **Upstash 5초 초과 (P2).** `@upstash/ratelimit` 은 5초 안에 답이 없으면 `{ success: true, reason: "timeout" }` 을 돌려준다.
  - `route.ts:249` 는 `result.success` 만 보므로, `CONTACT_RATE_LIMIT_REQUIRE_SHARED=true` 여도 그 순간은 막지 않는다.
  - Upstash 가 느려지거나 멈출 때만 생긴다. 운영을 서버 한 대로 옮기면 Upstash 자체가 필요 없어질 수 있다.
- **정리 (P2).**
  - 폼이 보내지 않는 필드 다섯 개(`type`, `companyStage`, `bottleneck`, `desiredOutput`, `timeline`, `route.ts:405–418`)를 지운다. 폼은 `name`·`email`·`phone`·`message` 만 보낸다.
  - 카운터 키(`homepage:contact:ip|email`)에 들어가는 IP·이메일 원문을 해시로 바꾼다. BE-07 과 같이 결정한다.

### BE-03 — 검색 API (P2)

- `/api/search` 의 목록(약 38KB)은 빌드 때 이미 정해진다. 그런데도 GET 핸들러가 동적이라 요청마다 함수가 돈다.
  - 인스턴스가 새로 뜰 때마다 MDX 를 다시 읽는다.
  - `llms.txt/route.ts` 처럼 `force-static` 으로 바꾸면 된다.
- 새 검색 서버나 DB 는 들이지 않는다. 수임료 계산기는 브라우저 참고 계산으로 둔다. 확정 견적이나 결제가 필요해질 때 그때 설계한다.

### BE-04 — 고객 포털 진입 (문구 2026-10-06 완료, 도메인 이전 남음)

- 홈의 "무료 대시보드 시작하기"는 `clientPortalUrl` 로 간다. 거기에는 가입 경로가 없는 로그인 화면만 있다.
  아직 고객이 아닌 방문자는 갈 곳이 없었다.
- 2026-10-06: 홈과 `/portal` 의 단추를 「고객 대시보드 로그인」으로 바꿨다(QA 2026-10-04 P1-5).
  아직 고객이 아닌 사람은 홈에서 옆의 「알아보기」, `/portal` 에서 「기장 이관 상담하기」로 간다.
- 남은 것: 포털 주소가 `hometax-dashboard.vercel.app` 이다. 홈택스를 닮은 남의 도메인에서 비밀번호를 묻는 모양이라 신뢰가 떨어지고,
  피싱 필터에 걸릴 수 있다(추정). `meridianco.kr` 하위 주소로 옮기면 `constants.ts` 의 `clientPortalUrl` 만 바뀐다.
- 포털 앱의 기능·데이터는 이 저장소에서 확인할 수 없다. 홈 미리보기의 숫자는 예시이며, 그 캡션을 지우지 않는다.

### BE-05 — 계약 앱 `/contract` (P2, 주인 판단)

- taxchat 을 같은 도메인 아래에 rewrite 한다. 그래서 그 앱의 스크립트가 홈페이지 origin 에서 돈다.
- 같은 도메인을 유지할지(서브도메인으로 뺄지)는 주인이 정한다. 카메라 권한 예외와 rewrite 순서 규칙은 `AGENTS.md` 에 있다.
- 서버를 옮긴 뒤의 영향은 BE-08 에 적었다.

### BE-06 — 콘텐츠·세무 일정 자동화 (만들지 않는다)

- 정적 파일로 충분히 운영된다. CMS, 국세청 일정 자동 수집은 비개발자의 잦은 편집이 실제로 생길 때 다시 본다.
- 일정 보충 알림(`.github/workflows/schedule-check.yml`)은 기본 브랜치에서만 돈다. `main` 에 합쳐지기 전까지는 돌지 않는다.
  - 현재 일정은 2026-12-15 까지 있다.

### BE-07 — 개인정보 처리 고지 (2026-10-06 초안 게시, 주인·법무 검토 남음)

- **2026-10-06:** 주인 지시(「러프하게, 필수적인 것만, best practice 로」)로 초안을 올렸다.
  - `/privacy` 페이지를 두고 푸터 아래 줄 · sitemap · 사이트 검색에 넣었다. 문의 버튼 위에는 고지 한 줄을 달았다.
  - 동의 체크박스는 두지 않았다. 계약 전 상담 요청에 따른 처리(개인정보 보호법 제15조 제1항 제4호)라 고지로 갈음한다.
  - 보관은 FAQ 약속에 맞췄다: 계약으로 이어지지 않으면 상담 후 지체 없이 지운다.
  - 위탁은 Amazon SES(서울) 하나만 적었다. 우리 서버에서 도는 구성 기준이다.
  - **이 페이지를 `main`(운영)에 올리는 것은 아래 검토가 끝난 뒤다.** 운영이 아직 Vercel(미국)이면 그 줄부터 더해야 사실이 된다.
- **검토 때 정할 것:**
  - 처리 주체. 문의는 `mscpa@dscpa.co.kr` 로 간다. `dscpa.co.kr` 은 동성회계법인 도메인이고, `/about` 은 메리디안이 별도 법인이
    아니며 업무가 동성 계약으로 수행된다고 적는다. 그렇다면 처리 주체가 동성회계법인이거나, 동성의 메일 시스템이 적히지 않은
    수탁사다. 초안은 「메리디안(박민상 공인회계사)」으로 적었다.
  - 운영 서버를 우리 회사가 대신 운영한다면, 우리 회사도 수탁사(홈페이지 운영)인지.
  - `/contract`(taxchat)와 고객 대시보드에 각자 처리방침이 있는지 확인한다. 초안은 「각 서비스가 따로 안내」로 범위를 갈랐다.
    대시보드에는 있다(2026-10-04 QA). taxchat 은 확인하지 않았다.
  - 보호책임자 연락처에 전화번호를 넣을지(제30조 제1항 제6호 「전화번호 등」). 번호 자체가 아직 확인 전이다(QA P0-4).
  - 운영 서버가 정해지면 그 업체를 「처리 위탁」 표에 더한다. 운영이 Vercel 에 남는 동안 이 코드가 올라가면,
    Vercel(미국)과 Analytics 를 수탁 · 국외 이전으로 적어야 한다.
  - Upstash 를 켜면 수탁사에 더한다. Upstash 키 이름에는 IP·이메일 원문이 들어가고 약 20분(창의 두 배) 남는다.
    해시로 바꿀지도 이때 정한다. 메모리 카운터는 창(10분)이 끝나면 스스로 지운다(2026-10-06).
  - 메일함에서 실제로 지체 없이 지우는지(운영 관행).
- 아래는 초안 전의 조사 기록이다.

- 문의 폼은 이름·이메일·전화번호·본문을 받는데, 처리방침 페이지도 수집 고지도 없다. `/privacy` 는 404 다.
- **실제 흐름:**
  - 입력값은 Vercel iad1(미국)의 함수를 거친다.
  - Resend(미국 AWS us-east-1)를 지나 `siteConfig.email`(`dscpa.co.kr` 메일함)에 도착한다.
  - 2026-10-01 코드부터는 Resend 대신 우리 AWS 계정의 SES 서울 리전을 지난다. 이 코드가 운영에 올라가면 위 줄을 고친다.
  - Upstash 를 켜면 카운터 키에 IP·이메일 원문이 들어간다.
- FAQ(`src/lib/faq.ts:42`)는 "계약으로 이어지지 않으면 보관하지 않고 파기합니다"라고 약속한다. 메일함 보관 관행과 맞는지 확인해야 한다.
- **결정할 것(주인·법무):** 처리 주체, 목적, 보관·파기 기간, 국외 이전 고지, 수탁사 목록.
  - 문안이 정해지면 `/privacy` 페이지와 폼 아래 한 줄 안내를 붙인다.
  - 보유 기간이나 필수 동의 체크박스를 코드 쪽에서 임의로 만들지 않는다.

### BE-08 — Vercel 을 떠날 때 다시 만들 설정 (운영 이전 전 P0)

운영(`www.meridianco.kr`)은 아직 Vercel 이다. dev(`accounting.teamcredit.kr`, `next start` 컨테이너)와 비교해 아래 차이를 확인했다.

- **자격 증명.** 메일은 우리 AWS 계정의 SES 로 보낸다(2026-10-01). 새 서버에는 `no-reply@meridianco.kr` 로만
  보낼 수 있는 SES 키와 `CONTACT_FROM_EMAIL` 을 넣는다. Resend 키는 필요 없다.
  - dev 의 키(IAM `meridian-homepage-contact-dev`)를 운영에 옮겨 쓰지 않는다. 같은 인라인 정책으로 운영용 사용자를 따로 만든다:
    `ses:SendEmail`, 자원 `identity/meridianco.kr`, 조건 `ses:FromAddress = no-reply@meridianco.kr`.
- **`CONTACT_RATE_LIMIT_REQUIRE_SHARED`.** 이 값을 `true` 로 둔 채 Upstash 키를 빼면 모든 문의가 503 이 된다.
  - 서버 한 대라면 메모리 카운터로 충분하다. 이 값을 끄고 Upstash 를 빼는 편이 단순하다.
- **검색엔진 소유 확인.** `NEXT_PUBLIC_GOOGLE_SITE_VERIFICATION`, `NEXT_PUBLIC_NAVER_SITE_VERIFICATION` 은 빌드 때 HTML 에 박힌다.
  - 운영에는 메타 두 개가 있고 dev 에는 없다. 새 빌드 환경에 넣지 않으면 서치 콘솔 인증이 풀린다.
- **edge 헤더.**
  - HSTS: 운영에서는 Vercel 이 `max-age=63072000` 을 붙인다. `next start` 는 붙이지 않으니 edge(Caddy)에서 붙인다.
  - 캐시: `next start` 는 미리 만든 HTML 에 `s-maxage=31536000` 을 보낸다. 앞에 공유 캐시(주황 구름 등)를 두면 배포 뒤에도 옛 HTML 이 남는다. edge 에서 덮어쓰거나 공유 캐시를 두지 않는다.
- **`/contract` 전달.** Vercel 에서는 edge 가 rewrite 를 처리했지만, 이제는 Node 가 직접 대신 전달한다.
  - 전달 제한 시간이 기본 30초다(`next/dist/server/lib/router-utils/proxy-request.js:37`).
  - 신분증 사진 업로드가 느리면 끊길 수 있다(추정, 미측정).
- **잃는 것.** PR 별 미리보기 배포, 즉시 롤백, Analytics/Speed Insights.
  - Analytics 두 컴포넌트는 `VERCEL=1` 일 때만 렌더되니, 옮긴 뒤에는 저절로 빠진다.
  - dev 서버는 이전 SHA 이미지로 되돌리는 것까지만 한다.
- **CI.** `ci.yml` 은 PR 과 `main` push 에서만 돈다. `dev` push 는 서버 빌드가 성공하는지만 보고 테스트는 거치지 않는다.
  - 운영을 pull 방식으로 옮긴다면, 배포 대상 브랜치를 CI 통과 뒤에만 옮기도록 한다.

## 하지 않기로 한 것

두 분석이 모두 "하지 말라"고 했거나, 확인 뒤 기각한 것이다. 다시 제안되면 여기의 이유부터 본다.

- **문의 저장 DB, CRM, 관리자 화면, outbox·메일 큐.** 저장소가 새로 생기면 보관·파기 의무가 늘어난다. BE-01 만 고치면 유실은 막힌다.
- **idempotency 키.** 최악의 경우도 같은 메일이 두 통 오는 정도다.
- **제출자에게 자동 확인 메일.** 남의 주소를 넣으면 폼이 스팸 발송기가 된다.
- **CAPTCHA.** 스팸 증거가 없다. honeypot(`website`)과 최소 작성 시간, 링크 수 제한으로 충분하다.
- **헤드리스 CMS, 검색 서버, 마이크로서비스, 수임료 결제, 포털·계약 앱을 이 저장소에 다시 만들기.**
- **`X-Forwarded-For` 위조로 한도를 우회한다는 지적(기각).** dev edge(Caddy v2.11, `trusted_proxies` 없음)가 방문자가 보낸 값을 실제 접속 IP 로 덮어쓴다. 안쪽 NPM 은 거기에 덧붙일 뿐이다.
  - Cloudflare 주황 구름을 켜면 전제가 바뀌니 그때 다시 본다.
