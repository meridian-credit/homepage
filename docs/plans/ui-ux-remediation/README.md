## 1. 목표와 범위

현재 브라우저에서 보이는 디자인을 보존하면서 실제 고객의 탐색·문의·견적 경험을 고치고, 같은 화면을 더 안정적으로 유지할 수 있도록 프론트엔드를 정리한다. 전면 재작성은 하지 않는다. 기존 [통합 검토](../../reviews/2026-09-11/production-readiness.md)의 모든 항목은 아래 작업 또는 [백엔드 후속 목록](./backend-backlog.md)에 연결한다.

사용자 지시를 우선하여 **새 백엔드 API, DB, 인증, CRM, 외부 업무 앱 구현은 이번 수정 범위에서 제외하고 기록한다.** 기존 문의 API의 실패 처리도 백엔드 후속 목록에 명시한다. 프론트엔드의 오류 화면을 고쳤다는 이유로 해당 API 결함이 해결됐다고 표시하지 않는다.

회원가입 없는 영업용 사이트로 유지한다. 회원 개인정보 관리 시스템이나 일괄 동의 체크박스를 추가하지 않는다. 기존 문의 폼의 연락처 처리에 관한 안내는 별도의 내용 확정 항목으로만 남긴다. 새로운 필수 입력이나 동의 절차를 임의로 끼워 넣지 않는다.

이번 산출물은 **계획**이다. 앱 코드를 수정하거나 새 브라우저 검증을 완료한 것으로 취급하지 않는다. 이전 검토의 Chromium/WebKit 검사와 아래 초기 화면 캡처는 참고 자료이고, 전체 애니메이션 기준선은 실제 구현을 시작하기 전에 다시 수집해야 한다.

## 2. 변경 기준: 화면을 먼저 보고 코드의 역할을 정한다

현재 로컬 브랜치를 production build로 실행한 화면이 기준이다. 운영 URL은 다른 버전일 수 있으므로 무조건 기준으로 삼지 않는다. 시작 시 HEAD, 브라우저 버전, OS, viewport, DPR, 모션 설정, 실행 명령을 기록한다. 브랜치가 바뀌었으면 기존 결함의 존재부터 재확인한다. `prototypes/`와 기존 사용자 작업은 건드리지 않는다.

유지할 것은 브랜드 영상·워드마크·색감·폰트·여백·섹션 순서·장면 전환의 인상이다. 메뉴 키보드 실패, 숨겨진 본문, 잘못된 일정, 초점 탈출, 문의 정보 유실 같은 확인된 결함은 기준 이미지와 다르게 수정해도 된다. 이 차이는 작업별 `intentional-changes.md`에 이유와 전후 증거를 기록한다.

주석·예전 HTML·사용되지 않는 컴포넌트만 보고 디자인을 복원하지 않는다. 특히 코드의 2.5초 스크롤 정지가 실제로 나타나지 않으면, 중복 Lenis 제거 후 갑자기 강한 스크롤 잠금을 추가하는 결과를 피한다. 보이는 장면과 실제 스크롤 경험을 우선하며, 현재 코드가 가진 버그를 픽셀 단위로 보존하지도 않는다.

## 4. UI-00 — 브라우저 기준선 수집

### 화면과 상태 매트릭스

- 경로: `/`, `/about`, `/services`, 서비스 상세 9개, `/members`, `/clients`, `/portal`, `/pricing`, `/contact`, `/faq`, `/blog`, 글 상세 대표 유형, 없는 경로. 공개 글은 URL/메타데이터 전수 검사, 시각 검사는 표·이미지·긴 제목 등 서로 다른 템플릿을 선택한다.
- 전체 화면 순회: Chromium 데스크톱 1440×900, 모바일 390×844. 반응형 핵심 화면은 375×812, 768×1024, 960×900, 1280×800도 확인한다. CSS 실제 breakpoint를 찾은 뒤 경계 양쪽 ±1px도 검사한다.
- 브라우저: Chromium 중심 기준 이미지, WebKit 모바일 크기에서 주요 흐름, Firefox에서 탐색·폼·스크롤 smoke. 에뮬레이션과 iPhone 실기기 검사를 구분한다.
- 설정: normal motion / reduced motion, JS 비활성 또는 초기 로드 실패, 키보드만 사용, 200% 확대와 좁은 화면, 가로 회전·높이 변경, 저속 네트워크/미디어 실패.
- 상태: 첫 로드, 스크롤 진입·중간·종료, hover/focus, 메뉴/검색/팝업 열림, 오류/빈 결과, 뒤로/앞으로 이동, 새로고침, hash 직접 진입.

### 캡처 절차

1. 같은 환경에서 fonts ready와 핵심 이미지 준비를 기다린다. 고정 대기 시간만으로 준비를 판정하지 않는다.
2. 데스크톱·모바일 첫 화면과 주요 섹션별 viewport 캡처를 찍는다. full-page 이미지 한 장만으로 sticky/pin 동작을 판단하지 않는다.
3. 정상 모션에서 실제 wheel/PageDown/앵커 클릭으로 이동하는 영상·trace를 남긴다. 느린 이동, 빠른 연속 이동, 역방향 이동을 각각 수행한다. `scrollTo`만 사용하는 검사는 실제 관성·휠 이벤트를 대체하지 못한다.
4. 장면별 진행 지점에서 정지 캡처한다. 진행률은 페이지 전체 높이 대신 해당 장면의 실제 시작·끝을 기준으로 측정한다. 0/25/50/75/100%를 기본으로 하고 말풍선 전환·카드 합류 등 경계 직전/직후를 추가한다.
5. 영상 프레임·날짜·자동 회전 문구만 비교용으로 통제한다. 정적 스냅샷에서 영상을 동일 프레임으로 고정할 수 있으나, 실제 자동재생·poster·로딩·motion 검사는 별도로 수행한다. 애니메이션 전체를 끈 캡처로 모션 보존을 판정하지 않는다.
6. console/pageerror, failed request, 레이아웃 넘침, 현재 포커스, URL도 함께 기록한다. 실제 문의 발송과 외부 계약 제출은 자동화에서 차단한다.

권장 산출물: `artifacts/<commit>/<browser>/<viewport>/<route>/<state>.png`, 장면 영상, trace, `baseline-manifest.json`, `motion-inventory.md`. 큰 영상·trace는 CI 아티팩트에 보관하고 저장소에는 기준 설명·선별 이미지·다운로드 위치를 남긴다. 이번 `reference/`의 두 캡처는 전체 기준선을 대체하지 않는다.

## 5. UI-01 — 검증 기반과 안전한 업데이트

`node_modules/next/dist/docs/`의 현재 버전 Playwright·라우팅·메타데이터·production 가이드를 먼저 읽는다. 프로젝트에 Playwright 설정, 핵심 E2E, 도메인 테스트를 추가하는 계획이다. 실제 스크립트 이름은 구현 시 `package.json`에 등록한다.

- production build와 별도 테스트 포트 사용. 개발 서버만 통과한 결과로 인수하지 않는다.
- 테스트를 `smoke`, `flows`, `visual`, `motion`, `a11y`로 분리하여 실패 원인을 알 수 있게 한다. baseline 갱신은 결과 확인 후 의도한 차이에만 적용한다.
- 접근성 있는 role/name을 우선 locator로 사용하고 모션 장면에는 필요한 최소 `data-testid`를 둔다. CSS 내부 구현에 모든 테스트를 결합하지 않는다.
- 연락·외부 업무 요청은 Playwright route mocking으로 격리한다. 성공 mock은 “실제 접수 확인” 증거가 아니다. 서버 오류·timeout·429·오프라인도 fixture로 만든다.
- 검토 당시 감사 결과를 재실행하고, 구현 시점의 공식 보안 공지를 확인해 Next/eslint-config-next 및 관련 의존성을 호환 버전으로 업데이트한다. 과거 보고서의 후보 버전을 무조건 고정하지 않는다. override를 재평가하고 lockfile·서명 검증·기존 CI 보안 gate를 유지한다.
- 버전 업데이트 직후 먼저 주요 화면과 라우팅을 비교한다. 이 단계에서 디자인 리팩터링을 섞지 않는다.
- WebKit은 실제 HTTPS 조건에서 CSP를 포함해 검증한다. 이전 로컬 검사는 `upgrade-insecure-requests`를 응답에서 제거한 보조 검사였다. 테스트 편의를 위해 운영 CSP를 약화하지 않는다.

## 6. UI-02 — 문의와 견적 흐름

대상: `src/components/contact/contact-form.tsx`, `src/app/contact/page.tsx`, `src/components/pricing/calculator.tsx`, `src/lib/pricing.ts`, 서비스 상세 CTA, 공통 문의 옵션.

1. `serviceId`, 문의 출발 경로, 선택 조건, 견적 버전을 가진 공통 프론트엔드 문의 초안을 정의한다. 서비스 표시명을 API enum으로 직접 사용하지 않는다. `output`/`desiredOutput` 및 기존 허용 목록 불일치는 BE-01에 연결한다.
2. 서비스 상세에서 문의로 이동하면 선택 서비스와 상담 목적을 폼 위 요약으로 보여주고 수정할 수 있게 한다. 견적 경유 시 입력 조건·예상 금액·옵션이 함께 표시된다. 기존 `message` 링크도 호환한다.
3. 새 API 없이 현재 문의 `message`에 사용자가 확인할 수 있는 요약을 포함하는 연결을 우선 검토한다. 구조화된 저장은 BE-01 완료 후 연결한다. API가 무시하는 hidden field를 추가하고 완료했다고 하지 않는다.
4. 이름·전화·상담 본문은 URL에 넣지 않는다. 공개 가능한 계산 조건은 버전 있는 견적 링크로, 개인 문의 초안은 메모리 또는 필요한 최소 sessionStorage로 전달한다. 후자를 쓰면 만료·제출/취소 후 삭제·저장 실패 동작을 명시한다. draft ID용 새 API는 이번에 만들지 않는다.
5. 공유 견적 입력에서 옵션 중복 제거, 허용 값·정수·최소/최대·비정상 숫자·알 수 없는 버전 처리를 정의한다. 잘못된 링크는 조용히 엉뚱한 견적을 보여주지 않고 복원 불가 또는 기본값 적용 사실을 알린다.
6. 가격표 자체는 바꾸지 않는다. 매출·인원 구간의 직전/정확한 경계/직후, 옵션 조합, 초기 비용, 공유 링크 왕복을 독립 기대값으로 검증한다. 현재 중복 옵션 월 15만→22만원 재현은 회귀 테스트에 포함한다.
7. 문의 UI 상태를 idle/invalid/submitting/success/error로 구분한다. 제출 중 중복 클릭 방지, 실패 시 입력 보존, 오류 요약·필드 연결·`aria-live`, 다시 시도, 전화 문의 대안을 제공한다. 429는 재시도 안내, timeout은 접수 여부 미확정임을 표현한다.
8. 성공 문구의 수준은 실제 API 계약에 맞춘다. 현 API의 거짓 성공 문제는 UI만으로 해결할 수 없으므로 BE-01 미완료 시 실제 문의 신뢰성은 인수 제외/운영 차단 항목으로 남긴다.

완료 기준: 서비스 9종에서 문의 요약 유지, 견적 URL 왕복 일치, 뒤로 가기 시 조건 보존, 모든 모의 응답에서 입력·포커스·문구가 맞음. 실제 메일 배달 검증은 별도다.

## 7. UI-03 — 탐색·키보드·URL 상태

### 헤더와 메뉴

현재 헤더 크기·투명도·배치·열림 모션을 유지하면서 트리거/패널 포커스 경계를 다시 설계한다. 일반 사이트 탐색은 disclosure 패턴을 우선하고 application menu 역할을 무조건 붙이지 않는다. 클릭·hover·키보드 동작을 일치시키고 Tab/Shift+Tab, Enter/Space, Escape와 포커스 복귀를 정의한다. 패널로 이동하는 동안 blur 때문에 닫히지 않게 한다.

모바일 메뉴는 전체 배경(main과 footer 포함) 비활성화, 포커스 가두기, 닫은 뒤 버튼 복귀, body 스크롤 잠금/복원을 구현한다. 중첩 팝업이나 route 이동 후 잠금이 남지 않게 한다. 일정 팝업도 같은 overlay 규칙을 따른다. 메뉴 열린 상태의 viewport 변경과 뒤로 가기를 테스트한다.

### 검색과 고객 탭

검색의 pill 확장 디자인은 유지한다. loading/error/empty/results를 구별하고 실패 시 재시도한다. combobox·listbox 연결, 방향키 선택, Enter 이동, Escape 닫기, 조합형 한글 입력을 검증한다. 서비스 검색을 AI 상담처럼 설명하지 않는다.

`/clients#growing-ceo` 등 기존 링크를 유지하면서 URL의 고객 단계를 선택 상태로 복원한다. hash 직접 진입·뒤로 가기·탭 클릭을 같은 상태 계약으로 연결한다. 각 tab/panel ID와 label, roving tabindex/방향키/Home/End를 정리한다. 시각 디자인을 바꾸지 않고 잘못된 ARIA 계층을 수정한다.

### 블로그와 스크롤 복원

분류·검색·페이지를 URL 상태로 관리한다. 검색 입력마다 history를 무한히 쌓지 않도록 replace/push 정책을 구분한다. 없는 분류나 범위 밖 페이지도 처리한다. 글을 읽고 돌아오면 3페이지·검색어·분류·읽던 위치를 복원한다.

새 페이지 진입, 같은 페이지 hash 이동, popstate 복귀, 새로고침의 스크롤 정책을 문서화한다. 모든 pathname 변경을 강제로 0으로 보내는 로직을 제거/조정한다. 이 정책을 UI-05의 단일 스크롤 제어가 사용한다. 본문 바로가기와 고정 헤더의 anchor offset도 함께 검증한다.

완료 기준: 기존 재현 4건(하위 메뉴 닫힘, 모바일 푸터 포커스 탈출, 고객 탭 불일치, 블로그 목록 초기화)이 사라짐. 마우스·키보드·터치에서 같은 목적지에 도착.

## 8. UI-04 — 일정·메타데이터·콘텐츠·복구 UX

- 일정 데이터를 한 곳으로 합친다. 원천세 `2026-10-10 → 2026-10-12`, 부가세 예정신고 `2026-10-25 → 2026-10-26`을 반영한다. 근거는 [국세청 2026년 10월 일정](https://www.nts.go.kr/nts/ad/taxSchdul/selectList.do?mi=135747&taxMonth=10&taxYear=2026). 실제 구현 시 다시 대조한다.
- 서울 날짜 기준으로 D-day 계산. 자정·탭 복귀 시 갱신하고 이미 지난 일정으로 되돌아가지 않게 한다. 미래 일정이 없으면 “등록된 다음 일정이 없습니다”와 공식 일정 링크를 제공한다. 일정에 기간·대상·출처·검토일을 두고 “이번 분기”라는 문구를 실제 범위에 맞춘다. 날짜 fixture를 이용해 경계·만료를 테스트한다. 자동 수집 API는 만들지 않는다.
- `/portal` self canonical, 데스크톱 홈의 의미 있는 H1, 페이지별 한국어 title/description, 기본 공유 이미지, FAQ JSON-LD 안전 직렬화 공통화. H1은 기존 워드마크 크기·레이아웃을 유지하며 의미만 바로잡는다.
- `/pricing`은 현재 의도대로 내비게이션에 새로 노출하지 않는다. 검색 제외 의도라면 noindex와 크롤링 정책을 모순 없이 맞춘다. robots 차단만으로 noindex 전달을 기대하지 않는다. 공개 전환은 별도 제품 결정이다.
- 사례가 0개인 동안 빈 분류를 주요 메뉴에서 숨기거나 직접 URL에 정직한 빈 상태·관련 서비스/문의 경로를 제공한다. 가짜 사례·성과·후기는 생성하지 않는다.
- 세무 글 검토 주기, 오래된 검토일 경고, 서비스/관련 글 참조 검증을 콘텐츠 검사에 추가한다. 날짜만 최신으로 일괄 변경하지 않는다. 본문 세법 판단은 담당 편집 검토로 남긴다.
- 푸터 직함 중복, 오래된 `llms.txt`, 내부 영어 페이지 명칭, 잘못된 CTA·빈 링크를 점검한다.
- 한국어 404/오류 화면과 다시 시도·홈·문의 이동을 제공한다. 검색 오류를 결과 없음과 구별한다. 빈 화면/미디어 실패에서도 핵심 문구·CTA는 사용할 수 있어야 한다.
- 정보성 텍스트 대비·focus ring·터치 영역·200% 확대를 확인한다. 장식용 숫자의 대비 경고와 실제 읽어야 하는 텍스트를 구별한다.

### 구조 변경 순서

1. 장면마다 `입력(스크롤/시간/선택) → 표시 상태 → 종료/정리`를 기록한다. 코드 selector가 현재 DOM에 매칭되는지도 브라우저에서 확인해 살아 있는 동작과 잔재를 구별한다.
2. 우선 기존 ReactLenis provider를 단일 제어 후보로 두고 `PromoMotion`의 별도 생성/RAF를 제거하는 작은 변경을 검증한다. 동등한 경험을 만들 수 없으면 원인을 기록하고 장면별 native scroll 대안을 비교한다. smooth scroll 삭제를 코드 단순화만으로 결정하지 않는다.
3. 스크롤 소유자가 anchor 이동·history 복귀·overlay 잠금·일시 정지를 함께 관리한다. 잠금은 소유자/token별로 해제하여 한 장면 cleanup이 열린 메뉴의 잠금을 풀지 않게 한다. reduced motion·터치에서는 강제 정지/스냅을 피한다.
4. GSAP는 해당 root/ref 범위의 장면만 소유하고 자신의 context/timeline/trigger만 정리한다. `ScrollTrigger.getAll().kill()` 같은 전역 정리를 없앤다. scroller proxy가 필요하면 단일 소유자가 설치/해제하고 불필요하면 제거한다.
5. `PromoMotion`을 실제 장면 단위로 옮긴다. 한 장면 이전→전후 브라우저 비교→해당 legacy 블록 제거 순서로 진행한다. 같은 장면에 새 effect와 옛 effect가 동시에 붙는 과도기를 만들지 않는다.
6. `ServiceMerge`는 typed props, root ref, 측정값/배치 계산, 타임라인 생성/정리를 분리한다. 임의 px 보정은 실제 요소 크기·컨테이너·헤더 높이로 대체하되 최종 배치를 기준 화면에 맞춘다. 폰트 로드/resize 후 refresh는 과도하게 반복하지 않는다.
7. React가 선택 상태/데이터/의미 구조를 소유하고, 애니메이션은 지정된 transform/opacity만 소유한다. 포털 예시 데이터 변경을 `innerHTML`로 React DOM 위에 덮어쓰는 부분은 React 상태로 이전한다. 같은 속성을 React·GSAP·Motion이 동시에 쓰지 않게 한다.
8. 이관한 파일의 `@ts-nocheck`와 파일 전체 eslint-disable을 제거한다. 이벤트·observer·timer·RAF·media query 구독을 해당 소유자에서 정리한다. 라이브러리 숫자 자체를 줄이는 것은 성공 기준이 아니다.

### 모션 완료 기준

- 시작·중간·끝·역방향에서 영상/문구/카드의 배치와 순서가 기준과 일치하거나 의도한 차이로 기록됨.
- 느린/빠른 스크롤, PageDown/Home/End, anchor 점프, 장면 중 메뉴 열기, 뒤로 가기, resize에서 콘텐츠가 사라지거나 스크롤이 잠긴 채 남지 않음.
- `/ ↔ /portal ↔ /about ↔ /contact`를 10회 반복해도 활성 장면 수에 비해 timer/trigger/RAF가 누적 증가하지 않음. 필요 시 개발용 계측으로 확인하며 진단 UI를 제품에 노출하지 않음.
- 모바일·reduced motion은 현재의 읽기 쉬운 정적 배열을 유지하고 불필요한 pin·hold·snap이 없음. 모션 설정을 실행 중 바꿔도 정상 전환.
- JS 초기화 실패 시 주요 본문/CTA는 보임. SSR 콘텐츠를 전부 opacity 0으로 두고 성공한 effect만 기다리지 않음.
- 자동 이미지 비교와 사람이 확인하는 영상 검토가 둘 다 통과. 캡처 수치가 같다는 이유로 “느낌”과 읽기 시간을 검토에서 생략하지 않음.

## 10. UI-06/07 — 렌더링·성능·스타일 정리

SSR과 hydration 후 wrapper 구조를 안정화한다. `template.tsx`, AnimateOnScroll, responsive stage를 먼저 확인한다. 넓이 판단 하나 때문에 자식 전체를 재마운트하지 않게 하며, 모바일에서 데스크톱용 긴 sticky 빈 공간이 먼저 나타나는지 저속 로딩으로 확인한다. CSS 반응형을 우선하고 모든 페이지를 UA 기반 동적 렌더링으로 바꾸지 않는다.

히어로 영상에는 현재 영상에서 적절한 poster를 추출해 적용한다. 파일의 배경 crop과 밝기는 유지한다. autoplay 실패·저속·오프라인에서도 글과 CTA가 보이고, 불필요한 동시 다운로드와 화면 밖 재생을 줄인다. 기존 관측의 영상 2회 요청은 재현 후 원인을 찾는다. HTTP range 요청을 무조건 중복 전체 다운로드로 계산하지 않는다.

폰트는 실제 사용 weight/문자/서브셋과 렌더 차단 경로를 확인한다. preload는 꼭 필요한 것만 적용하고 한글 폰트 변화로 줄바꿈이 달라지는지 확인한다. asset 캐시는 운영 응답으로 검증하고 파일명 버전/해시와 함께 설계한다.

전역 CSS를 장면 단위 CSS Modules 또는 명확한 root 범위로 옮긴다. 색·간격·타이포·breakpoint 토큰을 정리하되 디자인 값을 일괄 재설계하지 않는다. 한 장면 이관 후 기존 override를 제거하고 전 경로 비교한다. build manifest나 콘텐츠 캐시는 실제 병목이 확인된 범위만 적용한다.

미사용 코드·자산은 import/CSS/동적 참조를 검사한 뒤 삭제 후보를 기록한다. 기존 추적 생성물 44개는 보관할 설계 증거와 반복 산출물을 구분한다. `.gitignore`가 기존 추적을 해제하지 않는 점을 반영하고, 개인 로컬 배포 실험 파일이나 `prototypes/`를 정리 대상으로 삼지 않는다.

성능 비교는 동일 장비·production build·네트워크 조건으로 3회 측정해 중앙값과 편차를 기록한다. 이전 단일 측정 62점/LCP 9.5초를 절대 합격선으로 쓰지 않는다. 모바일 LCP 2.5초 이내, CLS 0.1 이하를 개선 목표로 삼되 미달 시 원인과 잔여 작업을 명시한다. 운영 p75는 별도 관측이 필요하다. 성능 점수만 올리려고 주요 디자인을 없애지 않는다.

| 백엔드 경계 | demo/기존 API/미구현/외부 앱 목록 최신화, mock을 실제 연동으로 표시하지 않음 |

검사 실패를 baseline 일괄 재생성으로 덮지 않는다. 예외가 필요하면 재현·영향·후속 항목을 기록한다. 실패가 없던 저위험 문구 변경마다 전체 테스트를 반복하기보다, 공통 렌더링/스크롤 변경에는 넓은 검사, 국소 변경에는 해당 시나리오를 적용한다.

각 변경의 인수 자료는 변경 이유, 수정 파일, 전후 이미지/영상, 실행한 검증, 의도한 시각 차이, 남은 BE ID를 포함한다. 완료 상태는 **프론트엔드 개선 완료 / 백엔드 연동 대기 / 별도 업무 앱 검증 대기**로 나눠 표시한다. UI 작업 완료를 사이트 전체의 프로덕션 준비 완료라고 부르지 않는다.
