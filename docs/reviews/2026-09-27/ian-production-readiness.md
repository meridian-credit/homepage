# `ian` → `main` 배포 준비도 — Claude · Astra 독립 검토 통합

검토일: 2026-09-27 · 대상: `origin/ian` `936315b` · 비교: `origin/main` `db9e3a3` (운영 https://www.meridianco.kr)

main 은 ian 의 조상이다. 머지는 커밋 38개, 파일 394개의 fast-forward 다.

## 어떻게 봤나

두 검토자가 서로의 결과를 보지 않고 같은 질문에 답했다.

- **Claude (Opus 5.5)**: 이 워크트리에서 빌드했다. `next start :3100` 앞에 TLS 프록시 `:3443` 을 두어 운영 CSP 그대로 시험했다.
  Playwright 측정 스크립트, ego-browser 로 손으로 둘러보기, Lighthouse(로컬 ian 과 운영 main)를 썼다.
- **Astra (codex gpt-6-astra, medium)**: `/tmp/dual-astra-ian` 에 따로 둔 워크트리에서 빌드했다(`:3200`/`:3643`).
  원문은 [astra-independent.md](./astra-independent.md), 증거는 `/tmp/dual-astra-artifacts/` 에 있다.
- Claude 쪽 원문(Astra 보고서를 읽기 전에 고정한 것)은 [claude-independent.md](./claude-independent.md) 에 있다.

독립성에 흠이 두 군데 있다.

1. Claude 가 진행 중에 Astra 로그 한 줄을 보았다. Resend 오류 반환 이야기였다. 그 항목은 Claude 가 SDK 코드를 읽어 따로 확인했지만,
   독립 발견이라고 세지 않는다.
2. 두 검토자 모두 저장소 안의 [2026-09-11 검토](../2026-09-11/production-readiness.md)를 읽을 수 있었다.

## 판단 — 이 커밋 그대로는 NO-GO. 아래 네 건을 고치면 GO

두 검토자의 판정이 달랐다.

- **Astra: NO-GO.** 근거는 문의 메일 결함 하나다.
- **Claude: 조건부 GO.** 근거는 `/blog` 회귀와 일정 만료다.

통합 판정은 **NO-GO** 다. 막는 이유는 Astra 가 댄 것과 다르다.

- 메일 결함은 main 에도 똑같이 있다. ian 이 운영을 더 나쁘게 만드는 부분이 아니다.
- ian 이 새로 만든 결함은 `/blog` 쪽이다. Astra 는 이것을 놓쳤다.
- 메일 결함도 이번 릴리스에 같이 고친다. 9/11 검토에서 이미 "가장 먼저 고칠 버그"로 적혔는데 아직 남아 있다. 고치는 데 몇 줄이면 되고, 사이트에 하나뿐인 전환 경로다.

오래 미루면 대가가 따른다. 운영 main 은 **next 16.2.4** 로 돌고 있고, `npm audit` 결과가 critical 1, high 6 이다
(Server Components DoS, RSC 캐시 오염 등). 그래서 main 의 CI 는 2026-08-02 부터 줄곧 빨간색이다. ian(next 16.3.4)은 0건이다.

그러므로 아래 네 건은 이번 주 안에 끝낸다. 늦어질 것 같으면 **의존성 올림만 따로 main 에 먼저 낸다.**

## 머지 전에 고칠 것

### 1. `/blog` 정적 HTML 에 글 목록이 하나도 없다 — ian 이 만든 회귀 · Claude 만 발견 · VERIFIED

- `src/app/blog/page.tsx:67` 이 `<Suspense fallback={null}>` 로 `BlogContent` 를 감싼다. `BlogContent` 는 `useSearchParams` 로 `?cat=`·`?page=` 를 읽는다.
  그래서 미리 만든 HTML 에는 목록 자리가 비어 있다.
  - 9/11 검토 #13(뒤로 가면 목록 위치가 사라짐)을 고치다 생긴 부작용으로 보인다. main 의 `blog-content.tsx` 는 `useSearchParams` 를 쓰지 않았다.
- `/blog/*` 링크 수: 운영 **51개**, ian **0개** (`curl … | grep href="/blog/`).
  - JS 를 끄면 제목과 설명 세 줄만 남는다.
  - JS 를 덜 도는 수집기(네이버 등)에게 블로그 색인 페이지가 빈 페이지로 보인다.
- 레이아웃 이동:
  - Playwright 데스크톱 CLS 0.595
  - Lighthouse 데스크톱 CLS 0.72 (성능 73)
  - Lighthouse 모바일 CLS 0.909 (성능 **42**, 운영 99)
  - 목록이 늦게 들어오며 푸터를 밀어낸다.
- 조치: `/contact` 와 같은 방식으로 한다. `fallback` 에 전체(필터 없는) 목록 첫 페이지를 서버에서 그려 넣는다.

### 2. 메일 공급자가 거절해도 "접수 완료"로 표시된다 — main 에도 있는 결함 · 둘 다 · VERIFIED

- `src/app/api/contact/route.ts:476` 은 `await resend.emails.send(...)` 의 반환값을 버린다.
  설치된 SDK(`resend@6.12.2`, `dist/index.mjs:1071`)는 HTTP 오류가 나도 예외를 던지지 않고 `{ data: null, error }` 를 돌려준다.
- 결과: 키 폐기, 발신 도메인 미인증, 한도 초과, 공급자 장애가 생겨도 폼은 입력을 비우고 성공을 띄운다. 문의는 사라진다.
  - `RESEND_FROM_EMAIL` 이 없으면 발신자가 `onboarding@resend.dev` 가 되는데, 이것도 같은 경로로 조용히 실패한다.
- Astra 가 실제 route 를 불러 바깥 `fetch` 만 바꿔 재현했다. 공급자 **403 → route 200 `{success:true}`**. 메일은 보내지 않았다.
- 조치:
  - `const { error } = await …` 로 받아, 오류가 있으면 로그를 남기고 5xx 로 답한다. 폼의 기존 오류 처리가 입력을 지켜 준다.
  - 거절과 성공을 가르는 서버 테스트를 하나 넣는다.
  - 운영 환경에서 발신 도메인 설정이 맞는지 주인이 한 번 실제로 보내 확인한다.

### 3. 세무 일정이 2026-10-26 에 끝난다 · Claude(P0) / Astra(P1 에서 언급) · VERIFIED

- `src/lib/schedule.ts` 에는 두 건만 있다(10/12 원천세, 10/26 부가세 예정). 날짜 자체는 둘 다 맞다. 주말 조정도 반영했다.
  - 운영은 지금도 틀린 10/10·10/25 를 보여 준다. ian 이 이것을 바로잡는다.
- 10월 27일부터는 모든 페이지 헤더에 "등록된 다음 일정이 없습니다 · 국세청 일정"이 뜬다(`schedule-cube.tsx:37`).
  운영은 11/10, 1/25 까지 적혀 있었는데, ian 은 오히려 줄였다.

### 4. JS 가 돌기 전이나 꺼진 상태에서 문의 폼이 GET 으로 제출된다 · Astra 만 발견 · VERIFIED

- 미리 만든 `/contact` 의 `<form>` 에는 `method` 도 `action` 도 없다(`contact-form.tsx:121`). 확인한 태그: `<form class="space-y-8" aria-busy="false">`.
- JS 를 끄고 Enter 를 누르면 `/contact?name=…&email=…&message=…` 로 이동한다. 이름·이메일·상담 내용이 주소창, 방문 기록, 접속 로그에 남는다.
  문의는 전송되지 않는다(Astra 재현).
  - 수화 전 구간에도 같은 일이 생긴다. 모바일은 JS 가 331 KB 라 그 구간이 짧지 않다.
- main 의 폼 태그도 같다. 다만 ian 에서 `/contact` 가 정적 페이지가 되었으니 수화 전에 폼을 만나는 사람이 더 많아진다.
- 조치: `method="post"` 를 달아 주소창으로 새는 길을 막는다. 제출 버튼은 수화된 뒤에만 켜고, 그 전에는 이메일·카카오 안내를 보인다.
  정적 prerender 는 그대로 지킨다.

  - `GET /api/search`: MDX 와 서비스 데이터로 검색 목록을 만든다. 빌드 추적에 mdx 54개가 들어 있어 배포에서도 읽힌다.
- 바깥 상태는 둘뿐이다.
  - **Upstash Redis**(선택): 속도 제한 카운터. 없으면 프로세스 메모리로 대신하는데, 서버리스에서는 사실상 제한이 없는 셈이다.
    `CONTACT_RATE_LIMIT_REQUIRE_SHARED=true` 이면 막힌 쪽으로 닫힌다(503).
  - **Resend** 메일 기록.
- 그 밖의 외부 연결:
  - Vercel Analytics / Speed Insights
  - 카카오 채널 링크
  - 고객 포털 `hometax-dashboard.vercel.app` (별도 앱)
  - `/contract` → `taxchat-one.vercel.app` 리라이트 (별도 Vercel 프로젝트. 인증·DB·신분증 처리는 그쪽 몫이고, 이번 검토 범위 밖이다)
- 결제·인증·마이그레이션 코드는 이 저장소에 없다.

## UI/UX — 디자인 심사 시점

좋은 점:

- 남색·흰색·파랑 팔레트와 서비스 상세 틀이 일관된다.
- 4갈래 8서비스 구조는 평면 목록보다 훑기 쉽다.
- FAQ 를 별도 페이지로 둔 것이 쓸모 있다.
- 회계사 소개가 담백하고 책임자를 분명히 보여 준다.
- 문의 폼의 라벨, 회신 기대치("1영업일"), 대체 연락 수단이 분명하다.

거슬리는 점:

- **P1 유리 헤더 가독성.** 스크롤하면 뒤 본문이 선명하게 비쳐 ABOUT·SERVICE 글자와 겹친다.
  예: "4대 보험 사업주 부담…"이 메뉴 줄 위에 그대로 읽힌다. 모든 페이지, 데스크톱과 모바일 모두 그렇다.
  - 주석을 보면 흐림을 일부러 뺐다(첨삭 "유리가 너무 불투명하다"). main 은 `bg-background/90 + backdrop-blur-xl` 이었다.
  - 굴절 효과는 두고, 밝은 본문 위에서만 흰 막 불투명도(현재 0.66)를 올리는 절충을 권한다.
- 첫 화면이 브랜드 연출에 치우쳤다.
- `/portal` 은 자문사 소개라기보다 소프트웨어 출시 페이지처럼 길다.
- 11.25 px 라벨이 곳곳에 있고 모바일 홈에는 8–9 px 도 있다. 탭 영역이 24 px 미만인 곳이 있다(로고 20 px, "모든 글 보기" 15 px, 요금 슬라이더 16 px).
- 상담 대상은 40–60대 대표가 많을 텐데, 이 글자 크기는 작다.

## 잠재 고객 시점

1. **무엇을 하나?** 스크롤 한 번 뒤에야 "매일의 기장부터 … 회계사가 직접 맡습니다"가 나온다. 첫 화면에서 알 수 있어야 한다.
2. **나에게 맞나?** 대표 단계별 안내와 서비스 상세가 도움이 된다. "PA"·"IPO"는 설명 없이는 전문가 말이다.
3. **누가 책임지나?** 박민상 회계사 사진, 경력, "직접 답한다"는 문장이 신뢰를 준다. 소속 고지(동성회계법인)도 있다.
4. **얼마인가?** 첫 상담 무료와 범위 기준 견적만 공개한다. 계산기(`/pricing`)는 숨겨 둔 채다. 이 결정은 존중한다.
5. **어떻게 맡기나?** 버튼, 카카오, 이메일은 쉽다. 전화번호는 문의 페이지와 푸터에 없다.
   - 「업무경험」을 누르면 "이 갈래엔 아직 글이 없습니다"가 나온다. 실적이 없어 보인다. 첫 사례 글이 나올 때까지 갈래를 숨긴다.
6. **믿을 수 있나?** 문의가 조용히 사라지는 결함(#2)은 위의 신뢰를 한 번에 무너뜨린다. 고객은 무시당했다고 느끼는데, 회사는 문의를 받은 적조차 없다.
